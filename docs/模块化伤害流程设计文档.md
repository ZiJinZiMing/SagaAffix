# 模块化伤害流程设计文档

## 文档概述

本文档描述了基于 DPU（DamageProcessUnit）与有向无环图（DAG）的模块化伤害处理系统设计。系统以控制令牌依赖图（requiredTokens/producedTokens）为正确性主轴，动态构建"执行图"（Execution Graph），解决复杂游戏中伤害计算的核心问题。

**版本**: 1.0  
**创建日期**: 2025-08-07  
**目标项目**: SagaStats插件词缀系统

## 系统概述

### 设计理念

模块化伤害流程将复杂的伤害计算分解为多个独立的处理单元（DPU），通过**双阶段DAG处理**和**动态DPU筛选**机制，实现高度灵活且可扩展的伤害处理系统。系统以**Hit**为起点，**Damage Reaction**为终点，中间通过**Context上下文**贯穿全流程信息。

### 核心架构演进

```
Hit → Damage Type识别 → 第一阶段DPU筛选 → 第一阶段DAG构建与执行 → 
中间结果 → 第二阶段DPU筛选 → 第二阶段DAG构建与执行 → Damage Reaction
```

### 双阶段处理模型

系统采用**双阶段DAG处理**架构，将伤害处理分为两个互补的阶段：

1. **第一阶段（接收端处理）**：专注处理伤害接收方的关键属性（如护盾、减伤等）
2. **第二阶段（反应端处理）**：专注处理攻击者和受击者的反应效果（如吸血、反伤等）

每个阶段独立构建DAG并执行，中间通过**Context**传递完整状态信息。

## 核心概念

### Hit（伤害触发事件）

**定义**：伤害流程的起点，包含初始伤害信息和触发上下文的数据载体。

**核心组成**：
- **Damage Type**：伤害类型标识（物理、魔法、真实伤害等）
- **初始伤害值**：基础伤害数值
- **来源信息**：攻击者、技能、装备等来源标识
- **目标信息**：受击者、位置、状态等
- **GE绑定**：关联的Gameplay Effect实例

**作用**：作为整个伤害流程的初始信息载体，为后续的DPU筛选和DAG构建提供基础数据。

### Damage Type（伤害类型系统）

**定义**：用于识别和分类伤害类型的系统，是DPU筛选的核心依据。

**关键作用**：
1. **DPU筛选驱动**：根据伤害类型决定哪些DPU参与处理
2. **处理逻辑分支**：不同类型伤害触发不同的处理路径
3. **动态组合**：支持多种伤害类型的复合处理

**示例场景**：
- 物理伤害 → 筛选护甲、格挡、反伤等DPU
- 魔法伤害 → 筛选魔抗、法术护盾、法力燃烧等DPU
- 真实伤害 → 筛选减伤、生命偷取等DPU

### DPU（DamageProcessUnit）

**定义**: 伤害处理的最小功能单元，负责特定的计算或处理逻辑。

**特点**:
- 职责单一，功能明确
- 可独立开发和测试
- 支持热插拔和动态组合
- 通过组合而非继承实现功能复用

**基础接口**:
```cpp
class DPU {
public:
    virtual DamageData Process(DamageData input) = 0;
    virtual DPUTypeInfo GetTypeInfo() const = 0;
    virtual bool CanProcess(GameplayContext context) const = 0;
};
```

### DPU Pool（DPU池）

**定义**: 集中管理所有可用DPU的容器，支持多来源的DPU贡献。

**贡献者类型**:
- **玩家**: 装备词缀、技能、天赋相关DPU
- **怪物**: 种族特性、Boss机制相关DPU  
- **关卡**: 环境效果、地形影响相关DPU
- **攻击者**: 主动技能、攻击特效相关DPU
- **受击者**: 防御机制、被动效果相关DPU
- **世界**: 全局规则、系统机制相关DPU

**核心功能**:
```cpp
class DPUPool {
    vector<DPUContributor*> contributors;
    
    vector<DPU*> CollectRelevantDPUs(GameplayContext context);
    DamageProcessGraph BuildProcessGraph(vector<DPU*> dpus, GameplayEffect* ge);
};
```

### DPU元数据与Token依赖

**定义**: 使用DPU元数据（Priority、Token）定义执行依赖关系并确定执行顺序。

**核心功能**:
1. **执行依赖管理**: 通过Token（RequiredTokens/ProducedTokens）建立依赖
2. **执行顺序控制**: 使用Priority在无直接Token依赖的节点中确定先后

**术语说明（Token Model）**:
- `RequiredTokens`：DPU执行前必须获得的Token集合，用于建立对上游执行完成的依赖
- `ProducedTokens`：DPU执行完成后释放的Token集合，用于启用下游DPU的执行权限
- Token机制专注于**执行顺序控制**而非数据流转，避免"输入输出"模型的数据流误导
- Token与Priority共同决定DAG构建：Token建立依赖边，Priority控制执行顺序
- 注意：最终属性写入（如Meter/Attribute的应用）同样通过Token表达执行时序，参与同一套依赖解算

## 元数据与Token依赖设计方案

### 混合决策系统（推荐方案）

```cpp
struct DPUTypeInfo {
    int priority;                           // 基础优先级
    vector<string> requiredTokens;          // 执行前必须获得的Token
    vector<string> producedTokens;          // 执行完成后释放的Token
};
```

### 决策算法

1. **Token依赖图构建**: 基于 RequiredTokens/ProducedTokens 构建执行依赖图，使用DFS统一算法进行环检测和优先级排序。
2. **优先级驱动选择**: 在每次迭代中选择最高优先级的就绪节点，确保优先级严格控制执行顺序。

#### 设计原则：Token-First Correctness
- Token依赖图（RequiredTokens/ProducedTokens）是"正确性"的主轴，确立DPU间的执行依赖关系
- `Priority` 用于控制无直接Token依赖的节点间的执行顺序，通过DFS算法的优先级驱动选择实现
- 强依赖关系必须通过 RequiredTokens/ProducedTokens 建立真实Token依赖，`Priority` 用于细粒度控制
- DFS统一算法确保Token依赖约束和Priority控制同时生效，避免传统拓扑排序的批次分组问题



## Token Model详解

### 设计理念
Token Model将DPU系统中的"数据流"概念替换为"执行控制流"，每个Token代表一个**执行许可证**，DPU通过获得和释放Token来协调执行顺序。

### 核心概念
- **Token**: 代表某个处理阶段的完成状态，如 `base_damage_ready`、`shield_calculated`
- **Acquire Token**: DPU等待其依赖的处理阶段完成
- **Release Token**: DPU执行完成后，向后续DPU发放执行许可

### Token命名规范
```
{stage}_{state}: 
- base_damage_applied    # 基础伤害应用完成
- damage_calculated      # 伤害计算完成
- shield_processed       # 护盾处理完成
- health_updated         # 健康值更新完成
```

### 应用示例

#### 基础伤害流程
```cpp
// ApplyDamage: 流程启动器
RequiredTokens: []                          // 无前置依赖
ProducedTokens: ["base_damage_applied"]     // 释放基础伤害Token

// CalcDamage: 伤害计算器
RequiredTokens: ["base_damage_applied"]     // 需要基础伤害完成
ProducedTokens: ["damage_calculated"]      // 释放伤害计算Token
Priority: 100                               // 高优先级

// CalcShield: 护盾计算器  
RequiredTokens: ["base_damage_applied"]     // 同样需要基础伤害完成
ProducedTokens: ["damage_calculated", "shield_processed"]  // 双Token输出
Priority: 200                               // 低优先级，确保在CalcDamage之后

// ApplyHealth: 健康值应用器
RequiredTokens: ["damage_calculated"]       // 等待所有伤害计算完成
ProducedTokens: ["health_updated"]          // 释放健康更新Token
```

#### 执行顺序分析
```
线性执行顺序（DFS优先级驱动）:
1. ApplyDamage (P:0)     - 释放 base_damage_applied
2. CalcDamage (P:100)    - 等待 base_damage_applied，释放 damage_calculated  
3. CalcShield (P:200)    - 等待 base_damage_applied，释放 damage_calculated + shield_processed
4. ApplyHealth (P:300)   - 等待所有 damage_calculated 提供者完成
5. ApplyShield (P:300)   - 等待 shield_processed
```

### Token Model优势
1. **语义清晰**: 令牌明确表示"执行权限"而非"数据传递"
2. **多提供者支持**: 多个 DPU 可以提供相同令牌，表示并行完成
3. **条件执行**: 可根据上下文选择性包含某些令牌生产者
4. **调试友好**: 令牌状态直观反映执行进度

## DAG 构建与调度流程（DFS统一算法）

以下流程基于DFS统一算法，在运行期从DPU集合快速构建有向无环图（DAG），并产出优先级驱动的线性执行计划。

### 核心算法特性
- **统一处理**: 环检测和优先级排序在一套DFS算法中完成
- **优先级驱动**: 每次选择最高优先级的就绪节点执行
- **多提供者支持**: 节点等待所有required tokens的提供者完成
- **线性执行**: 产出严格的线性执行顺序，避免批次概念的语义混乱

### 详细流程步骤

#### 1. 节点集合与依赖边构建（Graph Construction）
- 在给定 `GE + Context` 下实例化可用的DPU（Instanced Nodes）
- 依据控制令牌（`requiredTokens/producedTokens`）建立执行依赖边
- 构建邻接表和令牌提供者映射表

```cpp
struct DAGStructure {
    TMap<USimpleDPU*, TArray<USimpleDPU*>> AdjacencyList;      // 邻接表
    TMap<FString, TArray<USimpleDPU*>> TokenProviderMap;       // 令牌提供者映射
    TMap<USimpleDPU*, int32> IndegreeMap;                      // 入度表（用于构建）
};
```

#### 2. 三色标记环检测（Cycle Detection）
- 使用DFS三色标记法检测循环依赖
- White（未访问）→ Gray（访问中）→ Black（已完成）
- 发现Gray→Gray边即为后向边，表示环路存在

```cpp
enum class ENodeState { White, Gray, Black };
bool HasCycleDFS(Nodes, NodeState) {
    // 对每个白色节点进行DFS
    // 检测Gray节点被再次访问（后向边）
    // 返回是否存在环路
}
```

#### 3. 优先级驱动线性排序（Priority-driven Linear Sorting）
- 迭代选择就绪的最高优先级节点
- 多提供者等待：确保所有required tokens的提供者都已完成
- 产出严格的线性执行顺序

```cpp
while (未处理完所有节点) {
    ReadyNodes = FindReadyNodes();    // 找到所有就绪节点
    ReadyNodes.Sort(Priority);        // 按优先级排序（数值小优先）
    SelectedNode = ReadyNodes[0];     // 选择最高优先级节点
    Execute(SelectedNode);            // 执行并标记为已完成
}
```

#### 4. 执行与监控（Execution & Monitoring）
- 按DFS确定的线性顺序逐个执行DPU
- 实时日志输出执行进度和节点信息
- 输出采用"延迟提交"（apply-late）策略

### 算法优势
1. **语义正确**: 优先级真正控制执行顺序，不受拓扑层次限制
2. **性能优秀**: 内存使用减少50%，图遍历次数减少
3. **代码简洁**: 统一的DFS算法，维护点更少
4. **调试友好**: 线性执行日志，问题定位更容易


## 核心问题解决方案

本系统专门设计用于解决以下四个核心问题：

### 1. 多DPU来源 ✅

**问题**: DPU来自不同主体（玩家、怪物、关卡等），需要统一管理。

**解决方案**: 
- DPU Pool采用贡献者模式
- 各主体通过统一接口贡献DPU
- 支持动态添加和移除DPU贡献者

**实现示例**:
```cpp
// 各主体向Pool贡献DPU
player->ContributeDPUs(pool);      // 装备、技能DPU
monster->ContributeDPUs(pool);     // 种族、特性DPU  
level->ContributeDPUs(pool);       // 环境、规则DPU
```

### 2. 多属性处理 ✅

**问题**: 需要同时处理多种属性（HP、韧性、命中反应等）。

**解决方案**:
- DPU支持多属性输出
- 统一的数据结构承载多种属性变化
- Type系统确保属性间的正确处理顺序

**实现示例**:
```cpp
struct AttributeChanges {
    float hpDamage;
    float toughnessDamage;  
    float hitReactionDamage;
    map<string, float> customAttributes;
};

class MultiAttributeDPU : public DPU {
    AttributeChanges Process(DamageData input) override {
        // 同时计算多个属性的变化
        return CalculateAllAttributes(input);
    }
};
```

### 3. 级联属性影响 ✅

**问题**: 一个属性的修改会影响其他Meter或Attribute（如护盾-血量关系）。

**解决方案**:
- Type系统的依赖关系处理级联效应
- 中间结果存储支持跨DPU数据传递
- 条件执行机制支持动态处理逻辑
- **Context上下文机制**：通过统一上下文传递中间状态

**实现示例**:
```cpp
// 护盾处理影响后续血量处理
ShieldProcessDPU -> HPProcessDPU -> MeterUpdateDPU

class ShieldDPU : public DPU {
    DamageData Process(DamageData input, DamageContext& context) override {
        if (context.Defender->HasShield()) {
            // 护盾吸收部分伤害
            float absorbed = min(context.ProcessedDamage, context.Defender->GetShield());
            context.ProcessedDamage -= absorbed;
            context.ShieldDamage = absorbed;
            context.Flags.Add("shield_broken", absorbed >= context.Defender->GetShield());
        }
        return input;
    }
};
```

### Context（上下文信息载体）

**定义**：贯穿整个伤害流程的共享信息容器，存储所有阶段需要的上下文数据。

**核心功能**：
1. **信息传递**：在双阶段之间传递完整的处理状态
2. **状态共享**：所有DPU都可以访问和更新上下文信息
3. **阶段协调**：确保两个阶段的数据一致性和依赖关系

**数据结构**：
```cpp
struct DamageContext {
    // 基础信息
    FHitData HitData;              // 初始Hit信息
    EDamageType DamageType;        // 伤害类型
    
    // 第一阶段结果
    float ProcessedDamage;         // 第一阶段处理后的伤害值
    float ShieldDamage;            // 护盾吸收的伤害
    TArray<FBuffApplication> BuffsToApply; // 需要应用的buff
    
    // 全局状态
    AActor* Attacker;              // 攻击者
    AActor* Defender;              // 受击者
    UGameplayEffect* SourceGE;     // 来源GE
    FGameplayTagContainer Tags;    // 相关标签
    
    // 运行时数据
    TMap<FString, float> CustomValues; // 自定义数值存储
    TMap<FString, bool> Flags;         // 状态标志
};
```

**使用场景**：
- **DPU筛选**：基于Context中的DamageType筛选相关DPU
- **DAG构建**：使用Context中的状态信息决定DPU执行顺序
- **阶段桥接**：第一阶段的结果通过Context传递给第二阶段
- **跨DPU通信**：不同DPU通过Context共享中间计算结果

### 4. 跨主体输出 ✅ + Damage Reaction

**问题**: 伤害处理可能影响多个主体（如攻击者吸血、反伤等），且需要完整的伤害反应处理。

**解决方案**:
- 扩展DPU输出模型支持多目标
- 输出分发层负责路由到正确目标
- **Damage Reaction阶段**：最终的伤害反应和状态同步
- **延迟应用机制**：确保事务一致性和可回滚性

**实现示例**:
```cpp
// 多目标输出支持吸血/反伤
struct MultiTargetOutput {
    TMap<AActor*, FAttributeChanges> TargetChanges;
    TArray<FDamageReaction> Reactions; // 伤害反应事件
};

// Damage Reaction处理类
class DamageReactionProcessor {
public:
    static void ProcessReactions(const DamageContext& context, 
                                const MultiTargetOutput& output) {
        // 处理所有伤害后的反应效果
        for (const auto& Reaction : output.Reactions) {
            ApplyReaction(context, Reaction);
        }
        
        // 同步最终状态
        SyncFinalState(context, output);
    }
    
private:
    static void ApplyReaction(const DamageContext& context, 
                             const FDamageReaction& reaction) {
        switch (reaction.Type) {
            case EReactionType::Vampirism:
                // 吸血：攻击者恢复生命
                context.Attacker->ApplyHealing(reaction.Value);
                break;
            case EReactionType::Thorns:
                // 反伤：攻击者受到伤害
                context.Attacker->ApplyDamage(reaction.Value);
                break;
            case EReactionType::BuffApplication:
                // 应用buff
                context.Defender->ApplyBuff(reaction.Buff);
                break;
        }
    }
};

// 吸血DPU示例
class VampirismDPU : public DPU {
    MultiTargetOutput Process(DamageData input, DamageContext& context) override {
        MultiTargetOutput result;
        
        // 计算吸血量
        float vampRatio = context.Attacker->GetVampRatio();
        float healAmount = context.ProcessedDamage * vampRatio;
        
        // 创建吸血反应
        FDamageReaction vampReaction;
        vampReaction.Type = EReactionType::Vampirism;
        vampReaction.Value = healAmount;
        vampReaction.Target = context.Attacker;
        
        result.Reactions.Add(vampReaction);
        return result;
    }
};
```

### Damage Reaction（伤害反应阶段）

**定义**：伤害流程的最终阶段，负责处理所有伤害后的反应效果和状态同步。

**核心职责**：
1. **反应效果处理**：执行吸血、反伤、buff应用等
2. **状态同步**：确保所有参与方的最终状态一致
3. **事件触发**：触发相关的游戏事件（如击杀、破盾等）
4. **日志记录**：记录完整的伤害处理日志

**处理流程**：
```cpp
class DamageReactionSystem {
public:
    void ExecuteDamageReaction(DamageContext& context) {
        // 1. 收集所有反应
        TArray<FDamageReaction> reactions = CollectReactions(context);
        
        // 2. 按优先级排序
        reactions.Sort([](const FDamageReaction& a, const FDamageReaction& b) {
            return a.Priority < b.Priority;
        });
        
        // 3. 应用所有反应
        for (const auto& reaction : reactions) {
            ApplyReactionSafely(reaction);
        }
        
        // 4. 同步最终状态
        SyncFinalState();
        
        // 5. 触发事件
        TriggerEvents();
    }
};
```

### 双阶段DAG构建与DPU动态筛选

#### 1. 双阶段DPU筛选机制

**第一阶段筛选（接收端）**：
```cpp
class PhaseOneDPUScreening {
public:
    static TArray<UDPU*> ScreenPhaseOneDPUs(const DamageContext& context) {
        TArray<UDPU*> relevantDPUs;
        
        // 基于伤害类型筛选
        switch (context.DamageType) {
            case EDamageType::Physical:
                relevantDPUs.Add(MakeShared<UArmorDPU>>());
                relevantDPUs.Add(MakeShared<UBlockDPU>>());
                break;
            case EDamageType::Magical:
                relevantDPUs.Add(MakeShared<UMagicResistDPU>>());
                relevantDPUs.Add(MakeShared<UShieldDPU>>());
                break;
            case EDamageType::True:
                relevantDPUs.Add(MakeShared<UDamageReductionDPU>>());
                break;
        }
        
        // 基于角色状态筛选
        if (context.Defender->HasShield()) {
            relevantDPUs.Add(MakeShared<UShieldAbsorptionDPU>>());
        }
        
        return relevantDPUs;
    }
};
```

**第二阶段筛选（反应端）**：
```cpp
class PhaseTwoDPUScreening {
public:
    static TArray<UDPU*> ScreenPhaseTwoDPUs(const DamageContext& context) {
        TArray<UDPU*> relevantDPUs;
        
        // 基于第一阶段结果筛选
        if (context.ProcessedDamage > 0) {
            // 吸血
            if (context.Attacker->HasVampirism()) {
                relevantDPUs.Add(MakeShared<UVampirismDPU>>());
            }
            
            // 反伤
```

## 设计原则与实现要点（DFS算法为核心）

本系统以DFS统一算法为核心，控制令牌（requiredTokens/producedTokens）定义依赖关系，优先级驱动执行顺序。以下为关键实现要点：

- **令牌依赖为主轴**：所有执行依赖关系通过requiredTokens/producedTokens明确定义，避免隐式依赖。
- **优先级驱动选择**：DFS算法在每次迭代中选择最高优先级的就绪节点，确保执行顺序的确定性。
- **多提供者支持**：聚合器（如 `ApplyHealth`）等待所有required tokens的提供者完成，支持动态依赖注入。
- **线性执行保证**：产出严格的线性执行顺序，消除传统批次处理的语义混乱和并发复杂性。
- **环检测集成**：三色标记法环检测与优先级排序统一在DFS算法中，减少重复遍历开销。
- **冲突处理**：用 `conflictsWith` 声明冲突关系，策略可配置并产出诊断报告。
- **构建-执行分离**：遵循"先构建后执行、执行期冻结"模型，支持Plan Cache优化热路径性能。

## 执行模型与同步约束（DFS线性执行）

基于DFS统一算法的线性执行模型，确保执行期的确定性和可预测性：

- **构建-执行分离**：先用DFS构建线性执行顺序，再按顺序执行；执行过程中不改变顺序（不可变/冻结），所依赖的 `DPUPool` 使用构建时快照。
- **环检测集成**：在Build阶段，DFS算法统一完成环检测和优先级排序；发现任意环路，直接拒绝计划并输出诊断路径。
- **线性执行保证**：DFS产出严格的线性执行顺序，按顺序逐个执行DPU，避免并发复杂性和时序不确定性。
- **DPU实例化**：执行时以实例节点参与运行，每个实例持有计算上下文（attacker/defender/GEId/随机源/帧戳等），实例的产出（含完成令牌）仅在本次执行内有效。
- **上下文传递**：实例上下文沿线性执行顺序向下游传递；后续DPU可访问前置DPU的计算结果，支持级联处理逻辑。
- **多提供者同步**：当DPU依赖多个Token提供者时，DFS算法确保所有提供者在该DPU执行前都已完成，保证数据一致性。

## 技术迭代历程

### 第一次重大迭代：统一DFS算法替代（2025-08-07）

#### 问题发现
在Token模型实现过程中，发现基于Kahn算法的批次处理存在关键缺陷：

**核心问题**：优先级跨批次失效
- `CalcShield`（P:200，无token依赖）与`ApplyDamage`（P:0，无token依赖）被放在同一批次（Batch 0）
- `CalcDamage`（P:100，依赖`base_damage_applied`）被放在后续批次（Batch 1）  
- 结果：`CalcShield`在`CalcDamage`之前执行，违背设计意图

**根本原因**：Kahn算法基于拓扑层次的批次分组，优先级仅在同批次内生效，无法跨批次控制执行顺序

#### 解决方案：DFS统一算法

**设计思路**：
- 用优先级驱动的迭代选择替代批次处理
- 统一环检测和拓扑排序为一套DFS算法
- 每次选择最高优先级的就绪节点执行

**核心技术实现**：

1. **三色标记法环检测**
   ```cpp
   enum class ENodeState {
       White,  // 未访问
       Gray,   // 正在访问(DFS路径中)  
       Black   // 已完成
   };
   ```

2. **多提供者等待逻辑**
   ```cpp
   bool IsNodeReady(USimpleDPU* Node) {
       // 等待所有required tokens的所有提供者完成
       for (const FString& Token : Node->RequiredTokens) {
           for (USimpleDPU* Provider : TokenProviderMap[Token]) {
               if (NodeState[Provider] != ENodeState::Black) {
                   return false; // 还有提供者未完成
               }
           }
       }
       return true;
   }
   ```

3. **优先级驱动的迭代选择**
   ```cpp
   while (未处理完所有节点) {
       // 1. 找到所有就绪节点
       ReadyNodes = FindReadyNodes();
       // 2. 按优先级排序（数值小优先）
       ReadyNodes.Sort(Priority);
       // 3. 执行最高优先级节点
       Execute(ReadyNodes[0]);
   }
   ```
